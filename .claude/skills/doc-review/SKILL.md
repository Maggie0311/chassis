# 文档审查 Skill

## 功能说明

对项目文档体系进行结构化审查，确保：
1. 文档结构符合三层体系（L0/L1/L2）
2. 内容无过时、错误、虚构信息
3. 引用链路完整且深度合理

## 使用方式

### 全量审查（手动触发）
```
/doc-review
```
扫描整个文档体系，生成完整报告。

### 增量审查（指定范围）
```
/doc-review path/to/docs
```
仅审查指定目录下的文档。

## 审查流程

### 阶段 1：结构检查
1. 定位 CLAUDE.md（L0 根文档）
2. 识别 L1 任务类型指引文档（编译/探索/开发/测试/命令）
3. 追踪 L2 具体操作文档的引用链路
4. 检查命名规范和层级归属

### 阶段 2：内容验证
1. **路径验证**：文档中提到的文件/目录是否存在
2. **符号验证**：明确引用的函数/宏名称是否存在于代码中
3. **命令验证**：标记需要人工确认的命令（bash/python/编译命令）
4. **硬编码审查**：检查数值是否应该引用代码中的宏定义

### 阶段 3：引用分析
1. 计算引用链路最大深度（建议 ≤3 层）
2. 检测断链（指向不存在的文档）
3. 检测孤岛文档（没有被任何文档引用）

### 提前结束条件
- 首次审查：发现 20 个严重问题或扫描完 50% 文档时暂停
- 日常审查：发现 5 个严重问题时暂停
- 暂停时询问用户是否继续

## 问题分类

### 🔴 P0 - 立即修复（阻塞开发）
- 断链：指向不存在的文档
- 路径不存在：引用的文件/目录已删除或移动
- 虚构命令：文档中的命令在项目中不可用

### 🟡 P1 - 本周修复（影响协作）
- 符号不存在：引用的函数/宏已重命名或删除
- 内容过时：描述与当前代码实现不符
- 硬编码数值：应该引用代码中的宏定义

### 🔵 P2 - 有空再改（优化体验）
- 命名不规范：文件名不符合约定
- 缺少元数据：没有状态标记或更新时间
- 引用深度过深：超过 3 层嵌套

### 🟣 缺失文档
- 代码模块存在但缺少对应的设计文档或 README

### ⚪ 待人工复核
- 命令有效性（需要实际执行验证）
- 硬编码数值是否为客观事实

## 硬编码审查规则

**白名单（不审查）**：
- 芯片型号、引脚号、寄存器地址（如 STM32F334、PA5、0x40000000）
- 协议规定的固定值（如波特率 115200、I2C 地址 0x50）
- 物理常量（如 3.3V、16MHz）

**审查范围**：
- 定时器周期、缓冲区大小、中断优先级等业务参数
- 仅当能在代码中找到对应宏定义时，才建议引用该宏
- 找不到对应宏则标记为 ⚪ 待人工判断

## 符号验证范围

**必须验证**：
- 文件路径（如 `applications/main.c`）
- 明确引用的函数/宏（如"调用 `rt_kprintf()` 输出日志"）

**不验证**：
- 概念性描述（如"使用 RT-Thread 的线程机制"）
- 通用术语（如"中断处理"、"DMA 传输"）

**重构处理**：
- 符号不存在时，尝试模糊搜索相似名称
- 提示"可能已重命名为 xxx"

## 实现细节

### 文档扫描策略
1. 从项目根目录查找 CLAUDE.md
2. 解析 CLAUDE.md 中的链接，识别 L1 文档
3. 递归解析 L1 文档中的链接，识别 L2 文档
4. 记录引用关系和深度

### 路径验证方法
```python
# 伪代码示例
for doc in all_docs:
    for path_mention in extract_paths(doc):
        if not file_exists(path_mention):
            report_issue("路径不存在", path_mention, doc)
```

### 符号验证方法
```python
# 伪代码示例
for doc in all_docs:
    for symbol in extract_explicit_symbols(doc):
        if not grep_in_codebase(symbol):
            similar = fuzzy_search(symbol)
            if similar:
                report_issue("符号不存在，可能已重命名为 " + similar)
            else:
                report_issue("符号不存在", symbol, doc)
```
